# Hypotheses

## Part 3: Scaling (SIFT, 100K -> 300K -> 1M vectors)

**What is measured.** For each library size N (the first N SIFT vectors), the
time per query (single thread, one query at a time) of the cheapest setting
that reaches recall@10 >= 0.95, for exact search, IVF-Flat and HNSW. IVF-Flat's
number of lists grows with the data (nlist ~ sqrt(N) and 4*sqrt(N)).

**Hypothesis.** When the library grows 10x (100K -> 1M), the time per query at
recall 0.95 grows by about:

| Method   | Expected slowdown for 10x more data | Growth |
|----------|-------------------------------------|--------|
| Exact    | ~10x                                | proportional to N |
| IVF-Flat | ~3.16x (= sqrt(10))                 | proportional to sqrt(N) |
| HNSW     | ~1.5-2x                             | much slower than sqrt(N), closer to log(N) |

So the ordering of growth is: exact > IVF-Flat > HNSW.

**Why.**
- *Exact* compares the query with every stored vector, so the work is exactly
  proportional to the number of vectors.
- *IVF-Flat* compares the query with nlist centroids and then scans the nprobe
  nearest lists. With nlist ~ sqrt(N), each list holds about N / nlist ~ sqrt(N)
  vectors, and there are ~sqrt(N) centroids, so if the nprobe needed for 0.95
  stays about the same, the work grows like sqrt(N).
- *HNSW* walks a graph from neighbour to neighbour towards the query. A larger
  graph only adds a few extra hops (the upper layers let the search skip long
  distances), so the work should grow only slowly with N. It may need a
  somewhat larger efSearch at 1M to keep recall at 0.95, which is why we
  expect more than a pure log(N) increase.

**How we will judge it.** We fit the slope b of log(time per query) against
log(N) over the three sizes (time ~ N^b). The hypothesis is supported if
b(exact) ~ 1, b(IVF-Flat) ~ 0.5 and b(HNSW) is clearly below b(IVF-Flat),
i.e. the slowdown from 100K to 1M is roughly 10x, 3.16x and 1.5-2x.

## Part 4: Drifting data (generated by transforming SIFT)

**Question.** If an index is built on one distribution and new vectors then
arrive from a shifted distribution (added to the existing index without
rebuilding), which indexes degrade, how (recall or speed), and does
rebuilding from scratch fix it?

**Data (seeded generator).**
- *Old data:* 200K SIFT vectors (rows 0-199,999). The index is built on these.
- *New data:* 100K other SIFT vectors (rows 200,000-299,999), all moved by the
  same offset `alpha * spread * u`, where `u` is a fixed random unit direction
  and `spread` is the RMS distance of the old vectors from their mean.
- *Queries:* the SIFT query vectors moved by the same offset (they ask about the
  new kind of data). Tune on queries 0-4999, report on 5000-9999.
- *The one property varied:* the shift size `alpha` in {0 (control: new data
  from the same distribution), 0.5, 1, 2}.

**Indexes and protocol.** IVF-Flat (nlist=1024), IVF-PQ (nlist=1024, m=32) and
HNSW (M=16, efConstruction=200). Search settings are tuned once on the control
(the smallest nprobe / efSearch reaching tune recall 0.95; for IVF-PQ, which
cannot reach 0.95, the smallest nprobe within 0.005 of its best recall) and
then kept fixed for every shift. For each shift we measure recall@10 and
single-thread QPS in two versions:
- *stale:* built on the old 200K, then the 100K new vectors are added;
- *rebuilt:* built from scratch on all 300K (IVF centroids and PQ codebooks
  re-trained on the combined data).

**Hypothesis.** As the shift grows (stale version):
- *IVF-Flat:* speed drops a lot, but recall stays about the same or even rises.
  The list centroids were learned from the old data and do not move, so the
  shifted vectors are all assigned to the few centroids at the edge nearest to
  the new region. Those few lists become very large, and every query from the
  new region must scan them (slow), but they contain the true neighbours
  (recall holds).
- *IVF-PQ:* speed drops for the same reason, and recall drops too. On top of
  the list problem, the PQ codebooks were trained on residuals of the old
  data; the new vectors' residuals are much larger and point in a direction the
  codebooks never saw, so they are encoded poorly and many new vectors get
  near-identical codes. The index can then no longer tell which of them are
  really closest.
- *HNSW:* speed stays roughly the same, but recall may suffer. HNSW learns no
  summary in advance, but when the first new vectors are inserted there are
  few other new vectors yet, so their edges connect to less relevant (old,
  far-away) items. The graph inside the new region may therefore be of lower
  quality, and the search may miss some true neighbours.
- *Rebuilding* from scratch brings IVF-Flat and IVF-PQ back to their control
  numbers, and makes little difference to HNSW.
- The small shift (0.5) changes little; the effects grow with the shift.

**How we will judge it.** Compare each stale curve against the control
(alpha = 0) and against the rebuilt version at the same alpha. "Speed drops a
lot" means QPS falls by well over 2x at alpha = 2; "recall stays about the
same" means within ~0.02 of the control; "recall drops" means more than 0.02
below the control.
